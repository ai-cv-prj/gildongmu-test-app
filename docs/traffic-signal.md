# 신호등 모듈: SESAC-73

2026-09-22 기준 구현과 검증 기록입니다. 검출 실패와 안내 대상 선택 실패를 구분하며, 횡단보도 연결을 확정한 신호등이 정상적으로 추적되는 동안에는 다른 대상으로 교체하지 않습니다. 단일 검출로 고른 임시 대상은 여러 신호등이 보이면 횡단보도 기준으로 다시 선택합니다.

## 실행 전 가중치 준비

가중치는 Git에 포함되지 않아 `git pull`로 다운로드되지 않습니다. 모델 공유자에게 두 파일을 별도로 받아 저장소 루트 기준 `backend/models/traffic/best_YOLO_v2.pt`와 `backend/models/traffic/classifier/best_MobileNet.pt`에 넣어야 합니다. 색상 분류기까지 있어야 실제 신호등 모델을 로딩할 수 있습니다. 복사 명령과 확인 방법은 [README의 가중치 파일 넣기](../README.md#5-2-가중치-파일-넣기)를 참고하세요.

## 처리 흐름

1. YOLO가 보행자 신호등과 횡단보도를 검출합니다. 신호등은 IoU 0.60 이상으로 겹친 중복 검출 중 신뢰도가 높은 박스만 남긴 뒤 개수 판단·추적·선택을 진행합니다. 횡단보도 검출에는 이 중복 제거를 적용하지 않습니다.
2. YOLO는 추적 복구용으로 신뢰도 기준을 `min(0.1, 사용자 설정)`까지 낮춰 검출합니다. 세션별 Ultralytics BoT-SORT는 사용자 설정(기본 0.25) 이상인 신호등으로 새 추적을 시작하고, 0.1 초과·설정값 미만인 검출은 기존 객체와의 2차 매칭에만 사용합니다. 연결되지 않은 낮은 신뢰도 신호등은 화면·개수·대상 선택에서 제외합니다. 횡단보도에는 기존 사용자 검출 기준을 그대로 적용합니다. 이전 대상과 같은 ID가 현재 검출에 있으면 추적을 이어갑니다. 카메라 움직임은 BoT-SORT의 sparseOptFlow로 보정합니다.
3. 추적 대상이 없을 때 신호등이 하나면 임시 대상으로 바로 선택합니다. 여러 개면 횡단보도 선택 → 줄무늬 방향 추정 → 방향에 맞는 신호등 후보 선정 → 같은 신호등·횡단보도 3프레임 연속 확인을 거칩니다.
4. 단일 검출로 선택한 임시 대상은 여러 신호등이 보이면 색상 출력을 보류하고 횡단보도 연결을 3프레임 연속 확인합니다. 같은 대상이면 기존 번호를 유지하며 확정하고, 다른 대상이면 새 번호로 확정합니다. 횡단보도 연결을 확정한 대상은 정상 추적 중 다른 후보로 교체하지 않습니다. 미검출·매칭 모호 시에는 기존 대상을 즉시 해제하고 현재 프레임부터 3번의 선택 규칙을 다시 적용합니다.
5. 최종 선택된 현재 프레임의 신호등만 크롭해 MobileNet으로 색상을 분류합니다. 선택 보류 중에는 `unknown`을 반환합니다.

YOLO는 `predict()`로 검출하고, 그 결과를 Ultralytics의 실제 `BOTSORT`에 전달합니다. 공유 YOLO 모델의 `track(persist=True)` 상태가 휴대폰 세션 사이에 섞이지 않도록 트래커와 ID 발급기를 세션별로 분리했습니다. 중복 제거 및 신뢰도·추적 연결 조건을 통과한 현재 검출의 좌표는 그대로 보존하고 ID만 연결하며, 보이지 않는 예측 박스를 응답에 추가하지 않습니다. `track_id`는 선택 여부와 무관한 신호등 객체 ID입니다.

## 선택·유지·변경 조건

| 항목 | 현재 기준 |
| --- | --- |
| 신규 객체 신뢰도 | 신호등 모드 기본 0.25, 다른 모드 0.4. 사용자가 지정한 값 우선 |
| 신호등 추적 복구 신뢰도 | 기본 0.1 초과·0.25 미만은 기존 객체와 연결될 때만 사용; 새 추적 생성 불가 |
| 횡단보도 연결 신뢰도 | `CROSSWALK_CONNECTION_CONFIDENCE = 0.50`; 앱 검출 기준과 별도 상수 |
| 횡단보도 위치 | 박스 아래쪽 ≥ 화면 높이의 55%, 중심의 가로 편차 ≤ 화면 너비의 30% |
| 횡단보도 선택 점수 | 아래쪽 위치 비율 − 0.5 × 가로 편차 비율; 상위 두 후보 차이 ≥ 0.08 |
| 신호등 방향 후보 | 중심이 횡단보도 상단보다 위, 소실점과 가로 거리 ≤ 화면 너비의 22% |
| 신호등 후보 비교 | 방향 일치 점수와 최대 0.08의 크기 보조 점수; 상위 점수 차이 0.12 미만이면 모호 처리 |
| 후보 비교 예외 | 가로 방향 차이 ≤ 0.04이고 면적이 2배 이상이면 큰 박스 선택 가능 |
| 신호등 중복 제거 | 트래킹 전에 신호등 박스 IoU ≥ 0.60이면 낮은 신뢰도 검출 제거; 남은 박스 순서 유지 |
| 객체 추적 | Ultralytics BoT-SORT, sparseOptFlow 카메라 이동 보정, ReID 비활성 |
| 추적 설정 | match_thresh 0.8, fuse_score 미사용, 신규·고신뢰 기준은 사용자 검출 설정, 저신뢰 기준 min(0.1, 검출 설정) |
| 기존 대상 매칭 | 현재 실제 검출에 동일한 BoT-SORT ID가 하나 존재 |
| 연속 후보 확인 | 신호등 ID 동일 + 이동 보정한 횡단보도 IoU ≥ 0.30으로 기본 3프레임 일치 |
| 임시 대상 재선택 | 단일 검출로 선택한 뒤 복수 신호등이 보이면 횡단보도 연결 확인; 확인 중 색상 보류 |
| 확정 대상 유지 | 횡단보도 연결 확인 후 현재 검출과 명확히 매칭되는 동안 시간 제한 없이 유지 |
| 대상 소실·매칭 모호 | 기존 대상 즉시 해제 후 재선택 시작; 미검출 대상 보관 시간 없음 |
| 색상 분류 | 최종 대상만 분류; 분류 신뢰도 기준 0.60 |
| 상태 초기화 | 프레임 번호 불연속, 촬영 시각 역순 또는 1초 초과 간격, 해상도 변경 |

횡단보도 연결을 확정한 대상이 현재도 같은 BoT-SORT ID로 매칭되면 횡단보도 방향을 다시 평가해 교체하지 않습니다. 횡단보도를 놓치거나 다른 방향 후보가 나타나도 같은 신호등의 현재 색상을 분류합니다. 대상 교체를 위한 최소 2.5초 조건과 미검출 대상의 2.5초 보관 조건은 모두 제거했습니다. 트래커도 `track_buffer=0`으로 설정하고 매 업데이트 뒤 미검출 목록을 비워, 다음 프레임에서 소실 ID를 복구하지 않습니다.

단일 검출로 임시 선택한 대상은 여러 신호등이 보이면 횡단보도 기준으로 다시 확인합니다. 확인 중에는 선택 인덱스와 색상을 미확인으로 반환합니다. 확인 도중 다시 하나만 보이더라도 현재 임시 대상의 추적이 유지되는 동안에는 횡단보도 연결 확인을 마쳐야 색상을 재개합니다. 횡단보도·방향 근거가 없거나 후보가 모호하면 계속 보류하며 연속 확인을 초기화합니다. 연결이 확정되면 `selection_origin`을 `crosswalk_matched`로 바꿉니다.

추적 대상이 사라지거나 매칭이 모호하면 기존 박스·번호를 즉시 해제합니다. 같은 프레임에서 신호등이 하나면 바로 새 번호로 선택하고, 여러 개면 횡단보도 연결을 3프레임 연속 확인한 뒤 새 번호를 부여합니다. 새 연결이 모호하면 색상을 보류하며, 과거 박스나 색상을 출력하지 않습니다. 새 후보나 횡단보도가 바뀌거나 연결 근거가 끊기면 연속 확인을 초기화합니다. 프레임 불연속·해상도 변경 시에도 추적을 초기화합니다.

## 방향 추정과 흔들림 보정

`backend/app/inference/traffic/geometry.py`는 횡단보도 박스 안에서 밝고 긴 도색 줄무늬를 추출하고 양 끝점으로 경계선을 맞춰 교점을 추정합니다. 각 경계선은 최소 3개 줄무늬의 지지가 필요합니다. 화면·박스 경계에 잘린 끝점, 평행하거나 불안정한 교점, 근거가 비슷한 서로 다른 방향은 제외합니다. 기존 Hough 교점 투표 경로를 교체했으며, 기존 경로의 `numpy.int32` 좌표 처리 오류도 해당 경로 제거로 해소했습니다.

실제 신호등 ID 추적은 BoT-SORT가 담당합니다. 선택기는 해당 ID만 사용하며, 이전의 위치·크기 기반 자체 매칭과 자체 ID 발급 분기는 제거했습니다. 별도의 `backend/app/inference/traffic/motion.py`는 연속 확인 중인 횡단보도 후보가 있을 때만 좌표 보정을 위해 이전·현재 프레임의 특징점에 왕복 광류 검사와 RANSAC을 적용합니다. 최소 16개 일치점, 65% 이상 일치 비율과 화면 내 분포 조건 등을 통과한 이동만 해당 횡단보도 후보의 좌표 보정에 사용합니다. 실패하면 원래 좌표로 비교합니다. 검출 모델의 입력 영상을 안정화하는 기능이 아니며, 사라진 박스나 과거 신호색을 복원하지 않습니다.

## BoT-SORT 실행 환경

검증한 모델 패키지는 `ultralytics==8.4.150`, 객체 매칭 의존성은 `lap==0.5.13`입니다.
현재 프로젝트 가상환경에 lap을 설치했습니다. 다른 환경에서는 모델용 가상환경에
`.venv/bin/python -m pip install 'lap>=0.5.12,<0.6'`를 실행하세요.
GPU 환경이 다른 팀원에게 영향을 주지 않도록 공용 requirements.txt는 변경하지 않습니다.
외형 재식별(ReID)은 꺼져 있으므로 추가 모델을 내려받지 않습니다.

미확정 트랙도 현재 실제 검출에 연결된 ID는 즉시 사용합니다. 신호등 하나의 임시 선택과
대상·색상의 연속 확인 규칙은 유지합니다. ID가 아직 없는 검출은 화면에 남기되
`waiting_for_tracking`으로 색상 출력을 보류합니다. 프레임 불연속·해상도 변경 시에는
트래커와 선택 상태를 함께 초기화하며, 같은 세션 안에서 지난 ID를 재사용하지 않습니다.

이번 트래킹 연결은 테스트 앱에 적용했습니다. 별도 `gildongmu-integration` 프로젝트는
앞서 이식한 자체 추적 기반 선택 정책을 유지합니다.

## 화면과 저장 결과

미선택 신호등은 파란색, 확인 중인 후보는 노란색, 최종 대상은 굵은 박스와 안내 대상 문구로 구분합니다. 현재 프레임에 연결된 신호등 ID를 실시간 화면과 저장 영상에 표시합니다. 실시간 화면에서는 횡단보도 박스·라벨·검출 목록·진단 문구를 숨깁니다. 화면을 합성하는 WebM 녹화에도 횡단보도 박스가 표시되지 않습니다.

화면 하단에는 신호등 검출 개수와 안내 대상 선택·색상 상태를 표시합니다. 횡단보도 인식과 연결 판단은 내부적으로 계속 수행하고, 상세 진단은 저장 결과에 남깁니다. 서버에서 생성하거나 시각화 스크립트로 내보낸 영상과 모델 점검 이미지에는 횡단보도 박스와 탈락 사유가 표시됩니다. 이때 횡단보도는 보라색, 연결 판단에 사용된 횡단보도는 청록색이며, 청록색은 연결 성공을 보장하지 않습니다.

프레임별 `results.jsonl`에는 모든 신호등·횡단보도 박스와 다음 필드를 저장합니다. 선택·후보 인덱스는 현재 프레임의 `detections` 목록을 가리키며, 프레임 간 대상 식별자는 `track_id`입니다.

| 필드 | 의미 |
| --- | --- |
| `detections` | 신호등 뒤에 횡단보도를 추가한 전체 박스 목록 |
| `class_name` | 횡단보도 박스는 `crosswalk` |
| `track_id` | 신호등별 세션 내 BoT-SORT 객체 번호; 아직 ID가 없거나 횡단보도면 null |
| `extra.selection_status` | 신호등 선택 상태: `unselected` / `candidate` / `selected` |
| `event.selected_detection_index` | 최종 선택 박스의 현재 `detections` 인덱스; 미확정 시 null |
| `event.candidate_detection_index` | 확인 중인 신호등 후보 인덱스; 후보가 없으면 null |
| `event.detected_signal_count` | 중복·미연결 저신뢰 검출 제거 후 신호등 개수; 대상 선택에 사용하는 수 |
| `event.raw_detected_signal_count` | 추적 복구용 낮은 기준으로 얻은 YOLO 신호등 검출 수; 필터 적용 전 |
| `event.suppressed_signal_count` | 제거한 중복 신호등 검출 수 |
| `event.unmatched_low_confidence_count` | 중복 제거 후 기존 객체에 연결되지 않아 제외한 저신뢰 검출 수 |
| `event.crosswalk_candidate_count` | 표시 가능한 횡단보도 후보 수 |
| `event.detected_crosswalk_count` | 연결 신뢰도 0.50 이상 횡단보도 수 |
| `extra.crosswalk_status` | `below_confidence` / `position_rejected` / `eligible` / `used` |
| `extra.exclusion_reasons` | `below_confidence` / `bottom_too_high` / `off_center` 목록 |
| `event.crosswalk_diagnostics` | 검출·연결 상태, 후보·기준 통과 수, 사용된 횡단보도 인덱스 |
| `event.association_status` / `event.association_reason` | 기존 대상 유지 시 `tracked` / `previous_target_retained` |
| `event.selection_origin` | 단일 검출 `single_signal` 또는 연속 연결 확인 `crosswalk_matched` |
| `event.tracking` | `tracker=botsort`, 매칭 근거, 이전 대상 번호, 횡단보도 보정용 `camera_motion` |

`event.tracking.camera_motion`에는 보정 여부·실패 사유·일치점 수를 기록합니다. 추적 중 대상 재평가·교체 상태와 미검출 보관 시간 필드는 더 이상 생성하지 않습니다. 단일 검출 임시 대상의 `selection_origin`은 `single_signal`이며, 횡단보도 연결을 연속 확인하면 `crosswalk_matched`로 갱신합니다.

신뢰도 0.50 미만이거나 위치 조건에서 탈락한 횡단보도도 표시하지만, YOLO 검출 기준에서 이미 제거된 후보는 표시하지 못합니다. `selection_origin=single_signal`인 대상을 추적했다는 사실만으로 횡단보도 연결이 검증되지는 않습니다.

과거 기록에 저장되지 않은 박스나 상세 필드는 원본 프레임을 다시 추론해야 확인할 수 있습니다.

## 신호등 음성 안내

2026-09-22 추가했으며 현재 브라우저 버전은 `traffic-audio-v13`입니다. 서버는 기존의 선택 인덱스·대상 번호·신호색을 반환합니다. `guidance.js`가 관측 이력으로 문구를 결정하고, `tts.js`가 앱에 포함된 한국어 MP3 음원을 재생합니다. 관측 이력과 재생 상태를 다루는 초기 구현이라 안내 정책은 브라우저에 두었으며 별도 TTS 서버나 API 키는 필요하지 않습니다.

### 사용 상태와 안내 문구

테스트 전·중·후 언제든 `음성 끄기` / `음성 켜기`로 설정을 선택합니다. 기본값은 켜기이며 `gildongmu.prefs.voiceEnabled`에 저장해 다음 테스트와 페이지 새로고침 후에도 복원합니다. 설정 저장이 불가능하면 현재 페이지에서만 유지됩니다. 대기 상태에서 켜기를 선택해도 즉시 재생하지 않습니다. 켜둔 경우 테스트 시작 클릭 안에서 음성을 먼저 요청하고, 서버 세션이 생성되면 해당 세션의 추론 결과를 연결합니다. 꺼둔 경우 시작 음성을 포함한 자동 안내를 재생하지 않습니다. 테스트 중 끄기는 즉시 재생을 취소하고, 켜기는 현재 세션에 연결해 안내를 다시 시작합니다.

원거리 검출을 횡단보도 도착으로 간주하지 않으며, 관측된 신호 상태와 색상 변화를 읽습니다. 안내 시작 후 처음 확정된 신호가 초록불이면 다음 초록 신호를 기다려 달라고 한 번 안내합니다. 기존 신호 확인 이후의 대상 변경·감지 공백 복귀에는 이 대기 문구를 사용하지 않습니다. 시작 안내의 재생 완료 전에는 추론 결과가 음성을 취소하지 않으며, 완료 이전에 캡처한 프레임은 새 안내 근거에서 제외합니다.

### 관측·재생 기준

아래 값은 초기 테스트 설정이며 보행 안전성이 검증된 기준은 아닙니다.

- 같은 대상의 같은 색상을 최소 3프레임, 촬영 시각 기준 400ms 이상 확인한 뒤 안내합니다. 서버의 대상 선택 확인과 별도 조건입니다.
- 마지막으로 음성 안내를 요청한 색상은 추적 이력과 별도로 기억합니다. 대상 교체·미검출·통신 공백 뒤에도 소실 안내가 없었다면 같은 색은 화면만 갱신하고 음성은 반복하지 않습니다. “신호를 확인할 수 없습니다.”를 안내한 뒤에는 현재 신호색을 안정적으로 재확인하면 같은 색이어도 한 번 다시 안내합니다. 단순 후보 검출로는 이 재안내 조건을 해제하지 않습니다. 다른 색이 안정적으로 확인됐을 때 다시 안내하며, 확정되지 않은 반대 색 후보는 반복 억제를 해제하지 않습니다. 음성을 껐다 켜거나 새 테스트를 시작하면 이 기록도 초기화합니다. 소실 안내는 기존처럼 공백 구간당 한 번 유지합니다.
- 프레임 번호가 불연속이거나 촬영 간격이 1초를 넘으면 색상 전환 이력을 초기화합니다. 미선택·색상 판단 불가·처리 오류도 관측 이력을 초기화하지만 재생 중인 음성과 대기열은 유지합니다.
- 캡처부터 수신까지 1.5초 이상 지난 결과는 사용하지 않습니다. 브라우저의 동일한 단조 증가 시계로 비교합니다.
- 응답이 없어도 200ms 주기의 타이머가 확인합니다. 마지막 유효 관측의 촬영 시각에서 1초 초과 시 색상 전환 이력을 초기화합니다. 현재 재생 중인 안내는 끝까지 읽습니다. 현재 음성 안내를 켠 이후 신호색을 한 번 이상 안정적으로 확인한 경우에만 2초 이상 공백에서 판단 불가를 알립니다. 최초 미검출·미선택·짧은 검출에는 소실 음성을 내지 않습니다. 신호를 다시 안정적으로 확인하면 다음 소실 구간에서 한 번 더 안내하며, 음성을 껐다 켜거나 새 테스트를 시작하면 확인 이력을 초기화합니다.
- 새로운 안내는 대기열 끝에 넣고 현재 안내가 끝난 뒤 요청 순서대로 재생합니다. 색상 변경·대상 교체·미검출 때문에 현재 문장을 끊거나 이미 요청한 안내를 버리지 않습니다. 같은 색상 반복 억제는 그대로 적용합니다. 대기한 안내는 나중에 읽힐 수 있으며 화면은 최신 관측 상태를 표시합니다.
- 요청 시점에 이미 만료된 관측은 안내하지 않습니다. 대기열에 들어간 안내는 기다렸다는 이유로 만료시키지 않으며, 음원 로딩 제한 시간은 해당 안내의 재생 시도를 시작할 때부터 계산합니다. 재생 차단·음원 오류·종료 이벤트 누락 시에는 오류를 표시하고 재생과 대기열을 정리합니다.
- 안드로이드 Chrome에서 내장 TTS가 시작되지 않는 문제에 대응해 `SpeechSynthesis`를 고정 MP3 재생으로 교체했습니다. `static/audio/ko-v1/`의 일반 안내 7개·모의 안내 7개·음성 확인 1개를 같은 서버에서 제공합니다. 기기의 한국어 TTS 서비스나 실행 중 외부 합성 요청에 의존하지 않습니다. 문구·생성 출처는 해당 폴더의 `manifest.json`에 기록합니다.
- 테스트 시작·음성 켜기·음성 확인 클릭 안에서 같은 `Audio` 객체의 `play()`를 호출하고 이후 신호에도 재사용합니다. `playing` 이벤트 또는 재생 Promise의 성공을 확인한 뒤 재생 중으로 표시합니다. 재생 차단, 음원 로딩·디코딩 실패는 구분해 표시하고 안내를 종료합니다. [미디어 재생 API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play)
- 시작 안내와 음성 확인은 음원 로딩과 초기 준비를 위해 재생 시작을 최대 8초 기다립니다. 신호색 안내는 요청 시점의 남은 유효시간을 재생 시도 시작 후 로딩 제한으로 사용합니다(최대 1.5초). 앞선 음성을 기다리는 시간은 이 제한에 포함하지 않습니다. 시작 이후 종료 이벤트가 15초 동안 없으면 오류로 종료하며, 이전 재생의 늦은 콜백은 무시합니다.
- `음성 확인`은 카메라·서버 세션 없이 직접 재생합니다. 선택한 켜기·끄기 설정과 별도로 확인 음원을 요청합니다. 이미 재생 중인 음성이 있으면 대기열에 넣어 끝난 뒤 읽고, 진행 중인 신호 안내는 계속 유지합니다. 설정 자체는 바꾸지 않습니다. 화면에 준비 중·재생 중·재생 완료·오류 상태를 표시합니다.
- 음성 끄기·화면 숨김·페이지 이탈·카메라 종료·테스트 종료 시 실제 재생과 대기열을 모두 비우며 켜기·끄기 설정은 유지합니다. 화면이나 카메라 복귀만으로 자동 재개하지 않습니다. 진행 중인 테스트에서 중단·오류 후 다시 안내하려면 음성을 껐다 켭니다.
- Mock 응답에도 선택 인덱스를 제공하며 모든 음성 앞에 “모의 신호”를 붙입니다.

### 검증 범위와 남은 작업

초록불 재확인 문구를 “초록불입니다.”로 줄이고 일반·모의 MP3를 교체했습니다. 사용하지 않는 `green-unknown.mp3`, `mock-green-unknown.mp3`는 삭제했습니다.

`traffic-audio-v13`의 음성·앱 테스트 108개가 통과했습니다. 소실 안내 후 동일·변경된 대상에서 빨강·초록을 다시 확인하면 한 번 재안내하고, 짧은 후보 검출은 재안내 조건을 소모하지 않는지 검증했습니다. 소실 안내가 없었던 짧은 끊김이나 대상 교체의 같은 색 반복 억제는 유지합니다.

저신뢰 검출의 기존 객체 연결을 적용한 뒤 서버 테스트 120개가 통과했습니다. 실제 BoT-SORT로 신뢰도 하락 시 동일 ID 유지, 저신뢰 새 객체 생성 차단, 미검출 이후 저신뢰 검출로 과거 ID 복원 불가를 확인했습니다. 파이프라인에서는 사용자 지정 기준, 실제 현재 박스·색상 분류 유지, 미연결 저신뢰 박스가 복수 대상 판단에 섞이지 않는 것과 횡단보도 기준 유지를 검증했습니다. 미검출 보관·예측 박스 표시는 추가하지 않았으며, 현장 깜빡임 감소율은 아직 측정하지 않았습니다.

`traffic-audio-v9`의 음성·앱 테스트 104개가 통과했습니다. FIFO 순차 재생, 대기 중 유효시간 경과 후 재생, 로딩 중 후속 요청, 이전 재생의 늦은 이벤트 무시, 중단·오류 시 대기열 제거, 관측 변화 시 재생 유지와 음성 확인의 순차 재생을 검증합니다.
